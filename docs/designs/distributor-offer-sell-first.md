## Problem Statement

A handover proposed a new productized offer ("sales & inventory dashboards for distributors", Power BI, $350-450 intro, 7-10 days) plus about 2-3 weeks of build work on gateling.com: pipeline changes, follow-up automation, CSV import, weekly metrics, message templates and a landing page. The founder's actual goal, in their words: "I want to make money and want to make it smart not hard", and "ignore this idea if it doesn't make sense."

The real question isn't how to build the distributor tracker. It's what makes money soonest with the least new work, and whether the distributor offer earns any build effort at all.

## Demand Evidence

- **Distributor dashboards: none.** No distributor (including Arabian Foods, an existing case-study client) has asked for reporting or complained about Excel. The offer comes from a plan, not from a customer.
- **Atelier system: weak but real.** Gateling built and runs a full management system for Atelier Alaa El-Kasry. The founder describes them as a "real but not paying much" client, so they are a working reference, not proof that others would pay full price.
- No paid sale of either offer to an arm's-length customer yet.

## Status Quo

- The outbound sales pipeline already exists and works: `/sales/today` buckets, append-only activity log, follow-up safety limit, demo-meeting provisioning (`docs/sales-pipeline.md`, ADR-0002).
- It holds about 44 atelier prospects. The founder says outreach has **"haven't really started."**
- So the gap is outreach volume, not tooling. Every hour spent building tracker features is an hour not spent contacting the 44 leads it was built for.

Market context (web search, 2026-10-22, indicative only):
- Egyptian freelancers on Khamsat list Power BI dashboards at about $5-$75. "A dashboard" is a commodity deliverable locally. Higher prices only hold when the scope includes data cleanup and modeling, or is sold on a business outcome.
- Small Egyptian/Gulf distributors already have vertical tools (e.g. FieldSales for van sales; ERPNext/Odoo apps). Their ERP may already produce reports, which weakens a "Power BI on your exports" pitch.
- Tailoring software with Arabic support exists (Daftra's tailoring module; Emeron in the UAE). None found is Egypt-specific and Arabic-first in the way Gateling's atelier system is. That's a possible edge, but not verified with buyers.

## Target User & Narrowest Wedge

- **Main bet:** Egyptian atelier owners (bridal/evening-wear rental and sale), the same profile as the 44 prospects. Wedge: the existing atelier system, demoed in a Gateling Meetings room, with Atelier Alaa El-Kasry as the reference.
- **Side experiment:** owners or commercial managers of small Egyptian food/FMCG distributors. Wedge: a free 20-minute "data check" that leads to a paid "Monday Report" setup (defined below). No dashboard pitch.
- Gap: no named human in either group has said they would pay. Finding one is the point of the sprint.

## Constraints

- Solo founder time. Outreach and building compete for the same hours.
- **Time budget:** the gateling-doctor assignment (from the previous office-hours session) is **paused for the 14 sprint days** (confirmed by the founder at approval, 2026-10-22).
- WhatsApp ban risk: no more than 2 unanswered follow-ups per lead (already enforced in `today-rules.ts`).
- `.env` points at the production Neon DB. Any seeding or migration must be confirmed first. The sprint adds no schema changes. The day-14 measurement is a read-only query.
- Demo and test data stay fictional. **The live Atelier Alaa El-Kasry system is never screen-shared**, because it holds their customers' personal data (names, phones, measurements, orders).

## Premises (all agreed by founder)

1. **Selling beats software right now.** The tracker exists and hasn't been run. No new tracker features until outreach has run 2 weeks and the numbers show what's missing.
2. **Sell the outcome, not "a Power BI dashboard".** The local market prices dashboards at freelancer rates. The distributor test pitches customers lost and stock-outs avoided.
3. **Test with zero code.** A sample on fictional data plus direct messages logged in the existing pipeline. "Did anyone book a call or pay a deposit" is the only metric. Deploying an existing app with configuration and fictional data counts as zero code; new features don't.
4. **Atelier first.** Already built, Arabic-first, has a reference client and 44 named leads. Distributors are a side experiment.

## Approaches Considered

- **A) Sell-first sprint: CHOSEN.** 2 weeks, zero code. Details below.
- **B) Build the trimmed handover** (`offer` column + status history + distributor landing page, about 1 day of CC work). Rejected for now because it's building ahead of evidence. It becomes the plan if the distributor test passes its gate.
- **C) Sell a reporting retainer to existing clients** (Atelier Alaa, Arabian Foods, $100-200/mo). Not chosen as the main path because the volume is tiny and depends on those relationships. It can still be offered opportunistically.

## Recommended Approach: Sell-first sprint

### Day 0 (at most 2 working days)

Each item has one gate:

- **No outreach happens on day 0.** Outreach starts on day 1 (`SPRINT_START`) at the earliest, so every sprint touch falls inside the measurement window. No distributor prospect is added before `SPRINT_START`.
- **Items 1-3** (price sheet, deployment model, Demo Atelier) block **scheduling the first demo**. Outreach may start on day 1 before they're done.
- **Item 4** (distributor sample) blocks the **first distributor message**.
- **Item 5** (reference call) must be **attempted** on day 0, but it never blocks outreach. If the owner is unreachable, outreach starts without the quote, and the call is retried within the first week.
- **Sprint clock:** day 1 of the 14 is the first working day after day 0, and the founder records it as a timestamp (`SPRINT_START`).
- **If an item misses the 2-day cap:** outreach still starts. Any reply asking for a demo before items 1-3 exist gets a demo slot no more than 3 working days out, and the item is finished before that slot. The 14-day clock does not shift.

1. **Atelier price sheet.** The founder writes down:
   - the setup price and monthly price (if any);
   - the deposit: 50% of setup, matching the handover's 50/50 terms;
   - what the deposit buys: a reserved setup slot and the start of onboarding, refundable if Gateling misses the delivery date;
   - how it's collected: InstaPay or bank transfer, with the receipt logged in `/sales`.
2. **Deployment model, fixed for the sprint: one copy per client.** Each new atelier gets its own deployment of `atelier-management-system` (own database, own subdomain, its branding and settings). Multi-tenancy is deferred until at least 3 paying ateliers justify it.
3. **Demo instance doubles as the setup dry run.** Deploy one per-client copy branded "Demo Atelier" with fictional data. This is the only system shown in demos. Time the deployment: that duration is the measured setup effort. Delivery to buyers is promised as **"live within 7 working days of the deposit"**, unless the dry run shows that's unrealistic, in which case the promise becomes the measured time plus 3 days.
4. **Distributor sample:** one "Monday Report" on fictional data (see the offer below), about half a day.
5. **Reference ask:** call the Atelier Alaa El-Kasry owner (see The Assignment).

### Atelier track (main)

1. Work `/sales/today` every working day. Its new queue serves up to 10 atelier leads/day (setting `00017`). Log every touch as an activity.
2. Every reply gets offered a demo on the Demo Atelier instance in a Gateling Meetings room (logged as a `demo_scheduled` activity, which provisions the room).
3. At the end of every demo that goes well, quote from the price sheet and ask for the deposit.
4. Target: contact all 44 existing leads plus any referrals within 14 days.

### Distributor smoke test (side)

**The paid offer: "Monday Report" setup, $350-450 intro, 50% upfront.**
- **Inputs:** the client sends 3 months of sales and stock exports (Excel/CSV from their ERP or sheets).
- **Deliverable:** one report with 4 pages: overview, customers who stopped or slowed ordering, SKUs at stock-out risk, and sales by route/rep.
- **Turnaround:** 7-10 days from receiving clean exports, plus a 30-minute walkthrough call.
- **Delivery:** a Power BI file (or PDF if they have no Power BI license).
- **Optional:** a monthly refresh retainer of $100-200, done by hand from new exports.
- All of it can be delivered manually. No gateling.com code is needed.

**How the leads are worked:**
1. Collect exactly **30** small food/FMCG distributors **that have a reachable mobile number** (Google Maps listings, exhibitor lists, LinkedIn plus a phone found on their site). A lead without a number doesn't count toward the 30.
2. Add them to `/sales` as prospects with `businessType = "distributor"` and tier C, in batches of 5 per working day for 6 days. That's about 1/3 of daily outreach, matching the "side experiment" weight.
3. **First touch:** open each new batch from the top of `/sales/leads` (default sort is newest first) and message it the same day. This bypasses the new queue, which would sort tier-C distributors behind atelier leads and spend the shared 10/day cap.
4. **After first touch**, the existing Follow-up and Overdue buckets in `/sales/today` surface them like any other lead.

### How results are recorded (both tracks)

| Gate metric | Recorded as |
|---|---|
| Contacted | first `whatsapp_sent` or `call` activity |
| Replied | a `whatsapp_reply` activity |
| Demo / data-check call booked | a `demo_scheduled` activity |
| Demo / call held | a `demo_done` activity |
| Deposit received | a `note` activity whose outcome starts `DEPOSIT` with amount and transfer reference (the lead also moves to `won`, but status alone is never counted) |

**Day-14 query** (one read-only SQL query; doesn't use the counter strip, which mixes tracks):
- **Scope:** `kind = 'prospect'` only, which excludes inbound website leads.
- **Atelier track:** prospects whose `businessType` is not `'distributor'` (null or any other value; the seeded atelier set uses rental/sale/both). The Atelier Alaa reference record is excluded by id. Since distributors are only ever added on or after `SPRINT_START` with `businessType = 'distributor'`, no lead can land in both tracks.
- **Distributor track:** `businessType = 'distributor'`.
- **Time window:** only activities with `createdAt` between `SPRINT_START` and the end of day 14 count. Pre-sprint seeded history counts toward nothing.
- **Counts:** per track, the number of distinct leads with at least one in-window activity of each type in the table. Deposits are counted only from in-window `DEPOSIT` notes.

## Success Criteria (day-14 decision gates)

Thresholds are the founder's starting guesses. They may be adjusted once on day 0 and are then frozen. The first matching row wins.

**Atelier gate:**

| # | Condition | Decision |
|---|---|---|
| 1 | Fewer than 40 leads contacted | Sprint not executed. Run it one more week as-is (once only), no conclusions, no building |
| 2 | 1 or more deposits | Double down: keep selling, deliver, build only what the tooling-pain list demands |
| 3 | 3 or more demos held, 0 deposits | Offer/price problem: revise price or terms and run 1 more week |
| 4 | 1-2 demos held, 0 deposits | Too few demos to judge: continue unchanged for 1 more week |
| 5 | 5 or more replies, 0 demos held | Pitch problem: rewrite the demo ask and run 1 more week |
| 6 | Fewer than 5 replies | Channel problem: switch to calls, referrals or in-person visits for 1 more week |

After any "1 more week", the gate runs once more with the same table. If the result is not row 2, the atelier offer is paused and the founder decides the next idea in a new session.

**Distributor gate** (first match wins; any deposit is always delivered, whatever row matches):

| # | Condition | Decision |
|---|---|---|
| 1 | 1 or more deposits | Build approach B, and deliver the paid Monday Report by hand |
| 2 | Fewer than 30 distributors contacted | Not executed: one extension week to reach 30, then re-run this table |
| 3 | 3 or more calls held, 0 deposits | Price/offer problem: one extension week offering a smaller paid pilot (1 page, $150) to those who took calls |
| 4 | 1-2 calls held, OR 1 or more calls booked but none held (no-shows, or scheduled after day 14) | One extension week: hold the booked calls, plus 15 more contacts with the same offer |
| 5 | 0 calls booked | Drop the distributor offer |

**Extensions:**
- **Row 2's "not executed" week** is separate. After it, the table is re-run once, and that re-run may grant at most one row 3/4 extension week.
- **A row 3/4 extension week** is the single extension. After it, either there's at least 1 deposit and we build B, or the offer is dropped.
- The distributor test therefore lasts 4 weeks at most. There are no further extensions.

**Tooling:** list what `/sales/today` made painful during the sprint. Only items on that list are candidates to build next.

### R3-1 — consistency (blocking)

**Problem**

> Day 0 now says the reference call never blocks outreach, but The Assignment still says 'Before contacting any new prospect, call the owner of Atelier Alaa El-Kasry this week.' The contradiction R2-3 named (Assignment gating outreach on the reference call) remains: the two sections give opposite instructions for the case where the owner is unreachable.

**Remedy**

> Reword The Assignment to match Day 0 item 5: attempt the call on day 0, start outreach regardless, retry within the first week.

### R3-2 — consistency (blocking)

**Problem**

> Day 0 lets outreach start before items 1-3 are done, i.e. potentially during day 0, but the sprint clock and the day-14 query only count activities created on or after SPRINT_START (the first working day after day 0). First touches sent during day 0 would be discarded, so a lead contacted on day 0 counts as not contacted unless it gets another in-window activity, distorting the atelier row 1 (fewer than 40 contacted) and distributor row 2 checks. The text also leaves unclear whether outreach is allowed during day 0 at all or only from day 1.

**Remedy**

> State that outreach starts on day 1 (SPRINT_START) at the earliest, or set SPRINT_START to the moment of the first outreach message so every sprint touch falls inside the window.

### R3-3 — consistency (blocking)

**Problem**

> The new row 2 grants an extension week and then re-runs the table, but the re-run can land on row 3 or 4, each of which grants another extension week. That contradicts 'After the single extension week, either there's at least 1 deposit and we build B, or the offer is dropped. There are no further extensions.' The plan does not say whether a re-run after a row-2 extension may extend again, so the distributor test could run 4 weeks or be dropped after 3 with too few calls to judge.

**Remedy**

> State the rule for the re-run: either row 2's week counts as the single extension (re-run decides only between row 1 and drop), or row 2 is a separate 'not executed' extension and the re-run may grant exactly one more row 3/4 week, then stop.

### R3-4 — completeness (blocking)

**Problem**

> The atelier track is defined by creation time (existed before SPRINT_START), not by businessType, while the distributor track is businessType = 'distributor'. Any distributor prospect added before SPRINT_START (e.g. a first batch entered during day 0 while item 4 is being prepared) or any other pre-existing non-atelier prospect would be counted in both tracks, inflating the atelier 'contacted' count toward the 40 threshold. The document does not assert that every pre-sprint prospect is an atelier.

**Remedy**

> Define the atelier track as kind = 'prospect' AND businessType = 'atelier' (setting it on the seeded set if not already), or explicitly exclude businessType = 'distributor' and require all distributor rows to be added on or after SPRINT_START.
